# ADR 0019: Networked Threshold Raccoon signing, and execution through an on-chain Raccoon verifier

- **Status:** Accepted for research and testnet use only. Not audited.
- **Builds on:** [ADR 0014](0014-qd-wallet-protocol-threshold-raccoon-with-stateless-derivation.md) (protocol), [ADR 0017](0017-shared-wallet-approval-policy-separate-from-raccoon-threshold.md) (approvals), [ADR 0018](0018-shared-wallet-trusted-dealer-keygen-and-hpke-share-delivery.md) (key generation).
- **Date:** 2026-11-14

## Context

A shared wallet could reach its approval threshold and hold an initialized T-of-N Threshold Raccoon key, but nothing produced a signature, and nothing on any chain could check one. A Raccoon signature is not secp256k1 ECDSA, so no externally owned account can be controlled by it (QD protocol analysis §2.1, route A).

## Decision

1. **Signing protocol: QD-Wallet Alg. 4, unchanged.** The existing `QdParty` state machine runs TRaccoon ShareSign 1–3 with QD-rerandomised shares. It runs in each selected signer's key worker. The backend only relays the public round messages:
   - round 1: commitment and row blinder;
   - round 2: commitment-share opening and pairwise MAC tags;
   - round 3: masked response share.
2. **Signers.** The active set is exactly T parties: the first T approvers, mapped to their party indices in the wallet key (ADR 0014 §7). Only those devices may start or join the session.
3. **Session binding.** The coordinator draws a fresh random 32-byte `sid` per session. It is unique in the store and never reused; a failed session is replaced by a new one, never resumed. Each signer's key worker also records every `sid` it used and refuses a repeat.

   A session header freezes:
   - proposal id and digest;
   - key generation;
   - membership version;
   - (T, N) and the active set;
   - derivation index and chain id;
   - account address and public-key hash;
   - execution message, sid and expiry.

   Every round message is signed by the sender's P-256 device key over the SHA-256 of the transcript so far (header plus all earlier messages). The signer's browser recomputes the expected message from the proposal it approved and its own derived account key, and refuses any session that differs.
4. **Validation.** Signers check commitments and MACs (TRaccoon). The coordinator also checks each round-2 opening against the round-1 commitment, failing the session as `invalid_commitment`.

   After round 3 the coordinator combines the public transcript and verifies the result. If verification fails, the session fails as `invalid_signature`; an unverified signature is never stored. This requires a Go port of the *public* parts of `qd-crypto` (`internal/qdraccoon`: wire formats, commitment hash, Combine, Verify). It is pinned to the TypeScript reference by known-answer transcripts and holds no secret material.
5. **Lifecycle.** At most one open session and at most one signature per proposal, enforced by unique indexes. Sessions last 10 minutes and expire lazily.
   - A selected signer may abort with a device-signed reason: `cancelled`, `participant_abort` or `signer_state_lost`.
   - Retries are explicit and capped at 5 attempts.
   - A membership change fails open sessions. A proposal that already has a verified signature is not superseded.
6. **On-chain verifier.** `QdRaccoonVerifier.sol` is a port of `verify` with the same parameters, encodings and hashes.
   - The public matrix A is expanded on chain from `seedA` with SHAKE256: a Keccak-f[1600] permutation in Yul, generated by a committed script. This is done once per `seedA` in 20 entries, stored as contract code. Nobody can substitute a matrix.
   - Ring products are exact integer negacyclic convolutions using one NTT modulo the 120-bit prime P = 2^120 − 25599, then reduced mod q. Every coefficient is below 2^110 < P/2. This is the same arithmetic as the two-prime CRT NTT in TypeScript, with half the transforms.
   - The norm bound is the exact integer ⌊B²⌋.
7. **Smart account.** `QdAccount` has no owner and no ECDSA key. Its only authority is a Raccoon signature under `pk_j`; it stores `keccak256("QD-VK-v1" ‖ pk_j)`. The signed message is:

   ```
   keccak256(abi.encode(EXECUTE_TYPEHASH, chainid, account, nonce, to, value,
                        keccak256(data), callGasLimit, validUntil, proposalDigest))
   ```

   Each field binds one property:
   - the chain id: cross-chain replay;
   - the account address;
   - the single-use nonce: replay;
   - the exact call;
   - the gas given to the call: griefing by a relayer;
   - the expiry: the proposal's;
   - the approved proposal's digest.

   The nonce is consumed even if the inner call reverts (`Executed(success = false)`), so a signature can never be replayed later.
   - **Addresses.** Accounts are CREATE2 deployments from `QdAccountFactory` (salt = public-key hash). The verifier and factory are deployed through the deterministic deployment proxy, so addresses are the same on every chain.
   - **Registration.** Each participant's key worker derives `pk_j` from its share and registers or attests it. A different value is refused and audited. Each browser shows the address as "derived and verified on this device" only when its own derivation matches.
8. **Relayer.** The API submits verified signatures, paying gas from a per-chain key (`RELAYER_PRIVATE_KEY_<chainId>`; development only, refused in production). It deploys missing contracts, expands the matrix (2 entries per transaction), creates the account, and checks the account nonce and balance. A setup transaction that is mined and reverts costs gas, so it is retried at most 3 times, 5 minutes apart, and then the execution fails. It simulates `execute`, persists the signed transaction before broadcasting, and marks the proposal confirmed only after a receipt with status 1 and a matching `Executed(success = true)` event. The relayer can delay or censor; it cannot move funds or change the call.

## Consequences

- **Gas** (measured on Anvil under each hardfork):

  | | Osaka (Fusaka) | Amsterdam (live on Sepolia since 2026) |
  |---|---|---|
  | `execute` | 10.7M | 11.0M |
  | Deploy verifier (once per chain) | 3.5M | 24.1M |
  | Deploy factory (once per chain) | 0.7M | 4.9M |
  | Matrix expansion, per entry (20 per key per chain) | 5.3M | 16.5M |
  | Account creation | 0.5M | 3.5M |

  `execute` is computation and stays under the EIP-7825 16.78M per-transaction cap. Amsterdam's EIP-8037 raises the cost of storing code; that state-creation gas is charged outside the EIP-7825 cap, which now bounds computation only. So the setup transactions exceed 16.78M in total gas but remain valid; this was confirmed against live Sepolia. The relayer therefore sizes gas from the node's estimate (×1.2, bounded by the block gas limit and a 60M ceiling), not from the EIP-7825 cap.

  On Sepolia the one-time setup costs ≈ 363M gas, a negligible amount of Sepolia ETH at current fees. The signature is 19,494 bytes of calldata.
- **Security model.** The security model is the paper's: semi-honest, trusted dealer, no proof against malicious signers. Commitments, MACs, transcript binding and verify-before-store catch the deviations we test for. A bad response share is detected (the combined signature fails) but not attributed to a party: there is no identifiable abort.
- **Fixed signers.** Signers are fixed to the first T approvers. If one of them is permanently unavailable, that proposal cannot be signed; create a new one.
- **Rekeying changes addresses.** Account addresses depend on the key generation. After a membership change and rekey, accounts get new addresses. Funds must be moved out of the old accounts *before* rekeying, while the old shares still exist (there is no resharing).
- **Gas sponsor.** The relayer is a single gas-sponsor per API instance; several instances sharing one relayer key are not supported.
- **Audit and deployment status.**
  - The verifier, the Keccak permutation and the Go port are unaudited.
  - They have been tested against the TypeScript reference on Anvil only, not on a public testnet.
  - No ERC-4337 integration: submission is a direct call.
