# Shared wallets: networked Threshold Raccoon signing and on-chain execution

**Status:**
- **Implemented and tested end to end on Anvil:** independent devices, real cryptography, real EVM.
- **Not tested on a public testnet.** Research-grade, unaudited.

**Decision record:** [ADR 0019](../adr/0019-networked-threshold-raccoon-signing-and-qdaccount-execution.md). Earlier steps: [authorization](shared-wallet-authorization.md), [key generation](shared-wallet-key-generation.md).

## 1. End-to-end flow

```
proposal ──approvals (P-256, digest-bound)──▶ threshold reached ──▶ signing job (signers = first T approvers)
   │                                                                     │
   │   account key pk_j registered by a device, attested by others        ▼
   │   (address = CREATE2(factory, H(pk_j)))                       signing session
   │                                                               sid (fresh, unique), header frozen
   ▼                                                                     │
QdAccount execution message m = keccak(chainId, account, nonce, to, value, H(data), gas, validUntil, digest)
                                                                         │
 signer devices (key worker)          coordinator (wallet-api)           │
 R1: cmt_j, mask_j  ───────────────▶  relay; device sig over transcript ◀┘
 R2: w_j, MAC tags  ───────────────▶  check w_j opens cmt_j
 R3: z_j            ───────────────▶  Combine → Verify (Go port) → store signature, execution: pending
                                                                         │
                                       relayer: deploy verifier/factory (once), expand A (once per key),
                                       create account (once), simulate, send execute(call, pk, σ)
                                                                         │
                                       QdAccount: nonce, expiry, H(pk) check, QdRaccoonVerifier.verify
                                       → call → Executed(nonce, m, digest, success)
                                                                         │
                                       receipt status 1 + Executed(success = true) ⇒ Confirmed
```

## 3. What each device checks before it signs

1. The proposal digest, recomputed from the displayed fields.
2. Its own `pk_j`, derived from its share. The proposal's sender address must equal `CREATE2(H(pk_j))`.
3. The execution message, recomputed from the proposal and that address.
4. The session header: every frozen field, including the active set and the sid format.
5. Each round's inputs: every payload against its listed SHA-256, and every earlier round against what this device already saw. It then compares the transcript hash it computed itself with the coordinator's.
6. Inside the key worker:
   - the share belongs to the session's key generation;
   - this party is in the active set;
   - `H(pk_j)` equals the session's;
   - the sid was never used on this device.

   The TRaccoon commitment and MAC checks then run inside `QdParty`.

A mismatch aborts the session with a device-signed reason; it never produces a signature.

## 4. Statuses (`proposal.lifecycle`)

| Lifecycle | UI label | Meaning |
|---|---|---|
| `awaiting_approvals` | Awaiting approvals | Fewer than T approvals |
| `awaiting_key_generation` | Threshold reached — awaiting key generation | No initialized key matches the snapshot |
| `awaiting_account_key` | Threshold reached — awaiting account address | No registered `pk_j` for the sender account |
| `awaiting_signers` | Awaiting selected signers | Nothing sent yet |
| `signing` | Signing in progress | Rounds 1–3 (per-round progress shown) |
| `signature_verified` | Signature verified | Combined and verified by the coordinator; waiting for the relayer |
| `checking_relayer` | Checking relayer | Relayer reading chain state for this execution |
| `relayer_unavailable` | Relayer not configured | No `EVM_RPC_<id>` or `RELAYER_PRIVATE_KEY_<id>` in the API, or the RPC reports another chain id |
| `insufficient_account_funds` | Insufficient shared-account funds | The QdAccount holds less than the transfer value. Nothing is spent until it is funded |
| `insufficient_relayer_funds` | Insufficient relayer funds | The relayer cannot pay for the remaining setup and the execution at the current fee cap. Nothing is spent |
| `setting_up_verifier` | Setting up verifier | One-time setup: verifier and factory deployment, then public-matrix expansion |
| `preparing_account` | Preparing smart account | Deploying this key's QdAccount |
| `waiting_nonce` | Waiting for an earlier proposal | The account is below this proposal's nonce |
| `submitting` | Submitting to blockchain | Simulating, signing and broadcasting `execute` |
| `submitted` | Submitted — confirming | Transaction hash known (Etherscan link), no receipt yet |
| `confirmed` | Confirmed | Receipt status 1 and `Executed(success = true)` |
| `signing_failed` | Signing failed | Expired, aborted, invalid commitment or signature, membership changed. Retry opens a new session |
| `execution_failed` | Execution failed | Simulation reverted, nonce used, expired, reverted on chain, or the inner call failed |
| `rejected` / `expired` / `superseded` | — | As before |

The UI shows only steps that happened, are in progress or failed, never a future "Submitted" or "Confirmed".

## 5. The relayer

The relayer runs in `relayer.go` and processes executions one step at a time.

**Each pass:**
- **Re-reads chain state.** On-chain code, matrix entries and the account nonce are the source of truth for what setup is still missing. Contracts or entries that already exist are never deployed again.
- **Sends at most one transaction per execution and persists its hash before broadcasting.** A setup transaction is recorded as `pendingSetupTx` and later moved to `setupTxs`; the execute transaction is recorded as `txHash` plus the raw signed bytes. After an API restart, the relayer waits for the recorded transaction instead of sending another.

**Before spending anything,** it checks:
- the RPC's chain id;
- the account's code: a QdAccount bound to this verifier and key hash, at the factory's CREATE2 address;
- the account nonce;
- that the shared account can pay the transfer;
- that the relayer can pay the remaining setup and the execution at the current fee cap.

If any of these fails, it waits with a precise message and spends nothing.

**Setup reverts:** at most 3 attempts, 5 minutes apart, then *Execution failed*.

**One execute per account in flight.** Two approved proposals for one account can carry the same account nonce. Both would pass simulation against the state before either is mined, and the second would revert on chain (`BadNonce`) and still cost gas. This happened once on public Sepolia, in block 12138441. So while an execute for an account is in flight, the relayer holds any other execute for that account at *Waiting for an earlier proposal*. Once the first is mined, the other fails its nonce check without sending anything.

**`execute`:**
- **Simulate first.** It is simulated before it is sent; a revert sends nothing.
- **Broadcast errors.** If the node refuses the transaction outright (insufficient funds, nonce too low), it is re-signed later. Any other broadcast error keeps the recorded bytes, which are rebroadcast unchanged.
- **Confirmation.** *Confirmed* needs all of:
  - receipt status 1;
  - `receipt.to` is the account and `receipt.from` is the relayer;
  - the account's `Executed` event for the signed message;
  - the event's nonce, recipient, value and proposal digest equal the approved proposal's;
  - the event's `success` is true.
- **The device checks again.** Each device re-reads the receipt from the chain and checks it the same way (`apps/web/src/lib/verified-receipt.ts`). Only then does it render the receipt card and allow the PDF download (`lib/receipt-pdf.ts`).

**Diagnostics:**
- `GET /v1/relayers` (or `make relayer-status`) reports, per chain:
  - RPC reachability and chain id;
  - whether a relayer key is configured;
  - the relayer's address and balance;
  - the deterministic deployer and QD contract deployment status.

  It never includes key material.
- At startup the API logs the same information.
- Every error stored or logged has RPC URLs (which carry provider API keys) replaced by `<rpc>`.

**Configuration for `make api`:**
- **Secrets.** `EVM_RPC_11155111` and `RELAYER_PRIVATE_KEY_11155111` come from `.env` through Make's `export`, so they never appear on the echoed command line.
- **Persistence.** The development in-memory store is saved to `.data/dev-store.json` (`STORE_SNAPSHOT`, mode 0600, every 2 s and on shutdown). Wallets, proposals, signing sessions and execution progress survive API restarts. Restarting Anvil resets chain 31337 but not this file.

### Gas Service Account

The relayer address of each chain is that chain's **Gas Service Account**. It is one EOA per network, shared by every shared wallet on that network, and it pays gas for setup and execution. The shared smart account pays the transfer value. The key lives only in the API's environment (`RELAYER_PRIVATE_KEY_<chainId>`). No endpoint returns it, and the browser never signs with it.

**Settings → Network & Gas** (`features/gas-service/`, also linked from each proposal) shows:
- the network, the address with a copy button, a QR code and an explorer link;
- the live balance, gas price, health, pending requirement and estimated capacity;
- funding instructions, shown only after the API confirms its RPC serves that chain id;
- the history.

Funding is an ordinary external transfer to that address. QD Wallet never moves funds from a participant's wallet to pay for it.

**Health** (`GET /v1/relayers`, `gasservice.go`). Every requirement is an upper bound: the bounded gas from §5 × 1.2 headroom × the fee cap (3 × base fee + tip).

| Health | Condition |
|---|---|
| Insufficient | The balance does not cover the pending executions' remaining setup plus execute, or one execution when nothing is pending. |
| Low | The balance covers that, but not that plus the low threshold. |
| Healthy | Otherwise. |
| Unknown | The balance could not be read. It is never shown as zero. |

- **Pending setup** shared by several proposals of one wallet key is counted once.
- **Low threshold:** `GAS_LOW_BALANCE_WEI_<chainId>`. By default it is the cost of setting up one new wallet key and executing once at current prices.
- **Amounts** are rendered exactly. A requirement of 7,000 gwei is never shown as `0.000000`.

**Per proposal** (`GET /v1/proposals/{id}/gas-estimate`), the execution summary shows:
- the transfer amount and the shared-account balance;
- the gas service balance;
- the estimated gas requirement;
- the exact shortfall of whichever account is short;
- *Ready to execute* or the blocker.

It runs the relayer's own `preflight`, so the UI and the relayer cannot disagree, and it is read-only. When funds are short, the relayer re-reads balances every 20 s and sends nothing until they suffice.

**History** (`GET /v1/gas-service/{chainId}/history`, `gasmonitor.go`). Everything is read from chain receipts.
- **Outgoing.** The setup and execute transactions recorded on executions, linked to their proposal, with gas used, effective gas price and fee.
- **Incoming recharges.** These need no indexer. The monitor bisects the account's historical balance and nonce: a block range whose endpoints agree on both had no activity. It then reads only the blocks where they changed.
  - A balance increase that no transaction in its block explains, such as ETH sent by a contract, is recorded as an internal recharge.
  - A reverted transfer to the account moves nothing and is not listed.
  - The backfill covers 50,000 blocks (about a week on Sepolia) and needs an archive-capable RPC. Without one, history starts when the API starts.
- **Linking.** Proposal links are returned only to members of the proposal's wallet.

## 6. Running it

```
make anvil                       # chain 31337 on :8545
make api                         # now also sets RELAYER_PRIVATE_KEY_31337 (Anvil test account #1)
make web
make fund ADDRESS=<smart account address shown in the Accounts card>
```

**Manual test with three browser profiles:**
1. **Set up the wallet.** Create the wallet, invite two participants, run the key generation (see the key-generation doc §6).
2. **Derive the address.** In *Accounts*, add an account. Click *Derive smart-account address on this device* in one browser and *Confirm address on this device* in another. Fund the address with `make fund`.
3. **Propose.** Send 0.02 ETH on *Localhost (Anvil)*. The nonce is filled from the account.
4. **Approve.** Two participants approve. Keep both signers' pages open: their key workers sign automatically.
5. **Watch it complete.** The card goes through the rounds to *Signature verified*, *Submitted* (with the transaction hash) and *Confirmed in block N*, and the balance drops by 0.02 ETH.

### On Sepolia

Everything above works on Sepolia (chain 11155111). The contracts deploy to the same addresses on every chain. Two things differ:

1. **A funded relayer key.** Put `RELAYER_PRIVATE_KEY_11155111=0x…` in `.env` (a throwaway key; `cast wallet new`) and fund its address from a Sepolia faucet. `make api` passes it to the API together with `EVM_RPC_11155111`.
   - **First proposal:** the relayer first deploys the verifier and factory if they are not already on chain (once per chain, by anyone). It then expands the public matrix (once per wallet key, 10 transactions) and creates the account, ≈ 363M gas in total. At Sepolia's current fees this is far below 0.01 SepoliaETH, but it takes several minutes of blocks. The card shows *Submitting* with the relayer's last status in the meantime.
   - **Later proposals:** later proposals from the same account cost one `execute` (≈ 11M gas).
2. **Fund the smart account with SepoliaETH.** Send it from your personal Sepolia wallet in this app, or from a faucet, to the address in the *Accounts* card. Select *Sepolia* in the balance selector to watch it.

Then propose on network *Sepolia (11155111)*. The confirmed card's transaction hash can be opened on `https://sepolia.etherscan.io/tx/<hash>`.

## 7. Limits

The detailed list is in ADR 0019, *Consequences*. In short:
- semi-honest security only, with no identifiable abort;
- fixed signers;
- rekeying changes account addresses;
- the relayer is a development-only, single-instance gas sponsor;
- calldata is 19.5 kB and execution is about 11M gas;
- one-time setup per key per chain is ≈ 363M gas under Amsterdam (Sepolia), ≈ 130M before it.
